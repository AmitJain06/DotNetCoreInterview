Part 1 — Fundamentals & Entry Point (Q1–Q4)

Q1. Where is the Main method? Your Program.cs has no visible one.Fresher

With C# 10+ top-level statements, the compiler generates the Main method for me — every line in Program.cs becomes the body of a generated static Main (named <Main>$). The app starts with var builder = WebApplication.CreateBuilder(args); args are the command-line arguments passed to Main and later merged into configuration.

Q2. What does Microsoft.NET.Sdk.Web in the .csproj do?Fresher

It is the Web SDK. It references the Microsoft.AspNetCore.App shared framework, so all ASP.NET Core types (WebApplication, Kestrel, etc.) are available without installing NuGet packages. It also adds Web build targets: publishing behaviour, wwwroot handling and launchSettings.json discovery. A console project uses Microsoft.NET.Sdk and cannot call WebApplication.

Q3. Why are there no using statements in Program.cs?Fresher

Because <ImplicitUsings>enable</ImplicitUsings> is set in the .csproj. For the Web SDK, it auto-imports Microsoft.AspNetCore.Builder (so WebApplication and app.MapGet resolve), Microsoft.AspNetCore.Hosting, Microsoft.AspNetCore.Http, Microsoft.AspNetCore.Routing, plus Microsoft.Extensions.Configuration, DependencyInjection, Hosting and Logging.

Q4. Minimal API vs controller-based (MVC) app — what's different?Intermediate

A Minimal API uses top-level statements and inline lambdas (app.MapGet("/", () => "Hello World!")); there is no Startup.cs. An MVC app still starts in Program.cs, but registers builder.Services.AddControllers() and calls app.MapControllers(), and requests are routed to Controller classes. Minimal APIs are leaner (fewer allocations, less ceremony); MVC brings controllers, filters, model binding, validation and view engines out of the box.

Part 2 — The Core Lifecycle: CreateBuilder / Build / Run (Q5–Q9)

Q5. What happens on line 1: WebApplication.CreateBuilder(args)?Intermediate

It returns a WebApplicationBuilder and initialises the infrastructure:

  1. Configuration — loads appsettings.json, then appsettings.{Environment}.json, then (in Development) user-secrets, then environment variables, then command-line args.
  2. Environment — reads ASPNETCORE_ENVIRONMENT (set to Development by launchSettings.json).
  3. Hosting server — configures Kestrel and wires up IIS integration.
  4. Logging — registers the default providers: Console, Debug, EventSource, EventLog (Windows).
  5. DI container — creates the IServiceCollection and registers framework services (configuration, logging, lifetime, routing, server).

Nothing is listening yet — this is only the setup phase.

Q6. What does builder.Build() do?Intermediate

It is the construction phase:

  1. Validates the registered services (fail-fast on invalid registrations).
  2. Builds the IServiceProvider — the finalised DI container.
  3. Creates the WebApplication (app), which is at once the host, the request-pipeline builder (IApplicationBuilder) and the endpoint router (IEndpointRouteBuilder).
  4. Applies environment-specific default middleware: Developer Exception Page in Development; ExceptionHandler + HSTS + HTTPS redirection in Production.
Q7. What does app.Run() do?Fresher

It starts the Kestrel server, binds the configured URL (http://localhost:5279 here), and then blocks the main thread via WaitForShutdownAsync() so the process stays alive until Ctrl+C / SIGTERM triggers graceful shutdown through IHostApplicationLifetime.

Q8. The args passed to CreateBuilder — where do they come from and what's their purpose?Intermediate

They are the command-line arguments from the generated Main. The framework adds them as the last (highest-priority) configuration source, so they can override appsettings.json at runtime — e.g. dotnet run --urls http://localhost:5000 or overrides of any configuration key.

Q9. Which files get involved between dotnet run and the app serving responses?Fresher

dotnet run = build + execute. It uses:

  • TCS.csproj — defines the build (Web SDK, net8.0, implicit usings).
  • Program.cs — the bootstrap code itself.
  • Properties/launchSettings.json — run profile, port, ASPNETCORE_ENVIRONMENT (dev-only; not published).
  • appsettings.json + appsettings.Development.json — configuration and logging levels.

Part 3 — Configuration & Environment (Q10–Q13)

Q10. What is the configuration source order, and why does it matter?Intermediate

Later sources override earlier ones:

  1. appsettings.json
  2. appsettings.{Environment}.json
  3. User secrets (Development only)
  4. Environment variables
  5. Command-line arguments

That's why appsettings.Development.json can override appsettings.json, and secrets/env vars/args can override both. Values are exposed as a key-value map via IConfiguration and can be bound to POCOs with IOptions<T>.

Q11. How is appsettings.Development.json selected instead of appsettings.json?Fresher

The environment is resolved from ASPNETCORE_ENVIRONMENT (set to Development by launchSettings.json). The configuration builder then calls AddJsonFile("appsettings." + environment + ".json", optional: true) — it is only loaded if the file exists. Set ASPNETCORE_ENVIRONMENT=Production and the app looks for appsettings.Production.json instead.

Q12. What is ASPNETCORE_ENVIRONMENT, and what changes when you switch it?Intermediate

It is the runtime environment name read at startup. Besides selecting the environment config file, it changes the default middleware: Development gets the Developer Exception Page (rich stack traces); Production gets ExceptionHandler + HSTS. Your code can branch with app.Environment.IsDevelopment() via the injected IHostEnvironment.

Q13. What is in launchSettings.json, and does it get deployed?Fresher

It defines the run profiles (http, IIS Express), the application URL (http://localhost:5279) and environment variables. Crucially it is not deployed — it is only used by dotnet run and Visual Studio during development. In production, URLs/config come from ASPNETCORE_URLS or platform environment variables.

Part 4 — Dependency Injection (Q14–Q16)

Q14. How is DI involved in this 6-line app?Intermediate

CreateBuilder creates the IServiceCollection; Build() materialises the ServiceProvider. Even routing, logging, configuration and the web server are resolved through DI internally. Your own services would be registered via builder.Services.AddSingleton<IService, Service>(), then injected straight into minimal-API lambdas — e.g. app.MapGet("/data", (IMyService svc) => svc.Get()).

Q15. Explain the three DI lifetimes and when to use each.Intermediate
  • Singleton — one instance for the whole process (caches, HttpClient).
  • Scoped — one instance per HTTP request (EF Core DbContext, request-wide state).
  • Transient — a new instance every time it is resolved (cheap, stateless services).

Classic trap: never consume a Scoped service from a Singleton — the singleton outlives every request scope.

Q16. Is the built-in DI container enough, or do you ever need a third-party one?Senior

The built-in Microsoft.Extensions.DependencyInjection container covers the vast majority of apps: lifetimes, open generics, IServiceProviderFactory/IServiceCollection abstractions. Teams switch to Autofac/Scrutor/Microsoft.Extensions.DependencyInjection.AutoActivate when they need features the default lacks: decorators, keyed-by-convention registration, interception, or complex dynamic scanning.

Part 5 — Middleware & the Request Pipeline (Q17–Q22)

Q17. What is middleware, and how is a request processed in this app?Fresher

Middleware are components stacked into a pipeline; each request flows through them in order — each can act before/after calling the next, or short-circuit. In this app the pipeline is roughly: Developer Exception Page → Routing → your endpoint in Development, and ExceptionHandler → HSTS → HTTPS Redirection → Routing → endpoint in Production. The request enters Kestrel, travels down the pipeline, the matched endpoint's lambda runs, and the response flows back out.

Q18. What are Use, Map and Run in a pipeline?Intermediate
  • app.Use(...) — adds middleware that invokes next() to continue down the pipeline.
  • app.Map(...) — branches the pipeline by path prefix.
  • app.Run(...) — terminal middleware; it never calls next and ends the pipeline.

Note: app.MapGet("/", ...) is endpoint routing, not pipeline middleware.

Q19. In what order must middleware be registered?Intermediate

Registration order == execution order. Classic examples: UseExceptionHandler must be earliest (outermost) so it can catch exceptions from everything downstream; UseCors, UseAuthentication and UseAuthorization must run before endpoints; the terminal MapControllers()/MapGet go last.

Q20. Conventional routing vs endpoint routing — what's the difference?Senior

Modern endpoint routing separates route matching (UseRouting) from route execution (UseEndpoints/Map*). All routes are collected into an EndpointDataSource and matched by routing middleware — which lets middleware (like auth) run between matching and execution. Old-style UseMvc intertwined the two. Endpoint routing is also what powers Minimal API's MapGet.

Q21. What happens when you request http://localhost:5279/anything-else?Fresher

Routing matches no endpoint, so the client gets a 404. This app only registers GET /; every other path is unmatched, and the minimal template has no fallback page.

Q22. How does the Developer Exception Page help, and is it safe in Production?Intermediate

It renders detailed stack traces, query strings and headers to speed up debugging. It is not safe for Production (information disclosure), which is why production replaces it with UseExceptionHandler — a generic, friendly error page while details are only logged server-side.

Part 6 — Hosting, Kestrel & Advanced (Q23–Q30)

Q23. What is Kestrel?Intermediate

The default cross-platform, high-performance web server for ASP.NET Core, built directly on sockets (in-process in .NET 8). In production you usually run it behind a reverse proxy like IIS or Nginx that forwards requests to Kestrel: the proxy handles TLS, load-balancing and static content, while Kestrel does the application work.

Q24. WebApplication vs the old .NET Core 3.x IHostBuilder — what changed?Senior

WebApplication (added in .NET 6) unified IHostBuilder, IWebHostBuilder, the middleware pipeline and routing into a single builder for web apps, removing the old two-builder complexity and reducing overhead/allocation. In .NET 7+ you still opt into extra features via builder.WebHost (Kestrel/IIS options) or builder.Host (generic-host extensions like third-party containers).

Q25. How would you add your own services and middleware to this app?Intermediate 
builder.Services.AddScoped<IMyService, MyService>(); // DI
app.UseMiddleware<MyMiddleware>();                    // pipeline
app.MapGet("/data", (IMyService svc) => svc.Get());   // endpoint

The lambda automatically resolves IMyService from the DI container built in Build().

Q26. What is graceful shutdown and how is it triggered?Senior

Via IHostApplicationLifetime (ApplicationStarted / Stopping / Stopped). On Ctrl+C / SIGTERM the app stops accepting new requests, lets in-flight requests finish (within a configured timeout), disposes the IServiceProvider, then exits cleanly — rather than dying abruptly and losing work.

Q27. Explain the full request lifecycle in this app end-to-end.Intermediate
  1. Kestrel accepts the TCP connection and produces an HttpContext.
  2. Framework middleware runs (e.g. Developer Exception Page in Development).
  3. Routing middleware matches GET / to the registered RouteEndpoint.
  4. The endpoint middleware executes the lambda → "Hello World!" (or here, the questions page).
  5. The response is written with the correct content type (text/plain or text/html).
  6. HttpContext is disposed; the connection is reused via keep-alive.
Q28. If you deploy this to IIS, what does the app need to know?Senior

ASP.NET Core does not run inside IIS — IIS's ASP.NET Core Module (ANCM) reverse-proxies requests to Kestrel and surfaces the ASPNETCORE_IIS_HTTP_REQUEST env var, which the framework detects during CreateBuilder to enable IIS integration (forwarded headers, etc.). A web.config is only needed in the published output when hosting on IIS.

Q29. The app starts but returns 500 in Development — what do you check first?Intermediate

The Developer Exception Page should render the stack trace, so first confirm ASPNETCORE_ENVIRONMENT is actually set to Development. If it is set but no page appears, the failure likely happened before the pipeline (e.g. a config file failed to load or the server couldn't bind the port) — check the console logs and whether the port is already in use.

Q30. How do the http and IIS Express profiles differ in launchSettings.json?Fresher

They are separate run profiles: http runs the project directly on Kestrel at http://localhost:5279; IIS Express runs under IIS Express using the iisSettings section. Both set ASPNETCORE_ENVIRONMENT=Development and launch the browser. The profile is chosen in the IDE or with dotnet run --launch-profile — different ways of hosting the same Kestrel app.
